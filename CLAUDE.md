# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Hearthwise is a shared household app for two adults: chores, to-dos, a shopping list, recipes and a dinner plan, with one set of data and per-person views. React SPA + Auth0 (or built-in login) + AWS Lambda, or a self-hosted container on SQLite. Infrastructure is OpenTofu.

**Status: phase 5 (DIY projects) is built; phases 1, 2, 3 and 4 are built.** The Store, auth, API shell, container, infrastructure, brand, households, invites, chores and to-dos with proposals, the shopping list, offline use, and notifications exist. The finishing pass is in: wording test, accessibility checks, `DEPLOYMENT.md`, and the real-phone checklist `docs/MANUAL-CHECKS.md`, which a person must run. The approved design is `docs/designs/phase-1-foundation.md`; the phase 2 design is `docs/designs/phase-2-meal-plan.md` (drafted with the author away: its "Open Questions" list what to check first). The phase 3 design is `docs/designs/phase-3-money-tracker.md`; its real-phone checks are in `docs/MANUAL-CHECKS.md`. The phase 4 design is `docs/designs/phase-4-calendar.md`; its real-world checks are in `docs/MANUAL-CHECKS.md`, and the first is a real link from each of the four providers. The phase 5 design is `docs/designs/phase-5-diy-projects.md`; its checks are in `docs/MANUAL-CHECKS.md`. `docs/ROADMAP.md` lists the steps.

Hearthwise began as a copy of the scaffolding of a sibling app, Hoardwise, and shares an AWS account with it. Nothing here may point at the sibling's resources: see "Shared AWS account" below.

## Commands

```bash
yarn install          # Install dependencies
yarn dev              # Dev server with hot reload
yarn typecheck        # react-router typegen + tsc
yarn test             # Vitest (api project: node; app project: jsdom)
yarn build            # react-router build, then the static, API and push Lambda bundles
yarn build:container  # Compile the self-hosting server (container/) to build/container/
yarn store-cli        # Build and run the store command line tool (backup, reset-password)
```

`yarn test` runs the DynamoDB contract tests only when `DYNAMODB_ENDPOINT` is set (CI sets it). To run them locally: `docker run -d -p 8000:8000 amazon/dynamodb-local`, then `DYNAMODB_ENDPOINT=http://localhost:8000 yarn test`.

`yarn build` needs `VITE_AUTH0_DOMAIN`, `VITE_AUTH0_CLIENT_ID` and `VITE_AUTH0_AUDIENCE` for the AWS build. Container image: `docker build -t hearthwise:dev .` then `node scripts/container-smoke.mjs hearthwise:dev [--proxy|--tls]`.

## Architecture

- **Store** (`src/store/`): one interface over DynamoDB, SQLite and an in-memory store, shared contract tests. `transact` takes `put`, `delete` and a conditional `update` (`ifEquals`, `ifMissing`, `mustExist`). An attribute that is not set is left out, never stored as `null`. `expiresAt` is epoch seconds.
- **API Lambda** (`api-handler.ts`, `src/api/`): authenticates every request, then dispatches through a small router. Routes register in `src/api/apiRoutes.ts`. The router has `get`, `post`, `patch` and `delete`, and decodes path parameters once (a malformed escape is a 400).
- **Auth** (`src/auth/`): `AUTH_MODE` picks `auth0` (AWS default) or `local` (container default). Local login has one account per email; after first-run setup the only way to make one is an invite link (`signup-with-invite`).
- **Households** (`src/household/`, routes in `src/api/households.ts`): households, members, invites. **Every household route is wrapped in `withHousehold`** (`guard.ts`), which reads the caller's membership and hands the handler a `HouseholdContext`; the household id never comes from the request. Request fields are checked with the validators in `src/shared/validation.ts`. A member also has an optional `colour` (`hearth`, `honey` or `sage`, `MARK_COLOURS` in `src/shared/household.ts`) that both people see, saved through `PATCH /api/hh/members/me` and used by the calendar's cards (`app/lib/calendarPeople.ts`); it is on the member, not in `settings`, because settings are yours alone.
- **Tasks** (`src/tasks/`, routes in `src/api/tasks.ts`): `tasks.ts` (create, edit, delete, list), `completions.ts` (complete, undo), `ownership.ts` (who a task belongs to and what needs the other person's say), `proposals.ts`, `restore.ts`, `history.ts`. Dates and repeat rules are pure and shared: `src/shared/schedule.ts`; request validation: `src/shared/taskValidation.ts`. **Every write route carries a `mutationId` and runs through `withWriteRecord`** (`src/api/writeRecord.ts`): the write and its `MUT#` record are one transaction, so a retry is answered from the record and writes nothing. Read the record first (`replayOf`), then the task.
- **Shopping** (`src/shopping/`, routes in `src/api/items.ts`): `apply.ts` is the pure write rule (field timestamps, tombstones, clear-ticked), `items.ts` the domain (single writes inside `withWriteRecord`; a batch is one transaction per entry plus one record). Restore of an item is in `src/tasks/restore.ts`. The app reuses it: `app/lib/itemOverlay.ts` applies the same rule to pending writes, and item mutations (`itemMutationKeys`) are registered beside the task ones.
- **Meals** (`src/meals/`, routes in `src/api/meals.ts`): `applyRecipe.ts` and `applyPlan.ts` are the pure write rules (per-field times, tombstones for recipes; a plan day is never tombstoned), `recipes.ts`, `plan.ts` and `addToList.ts` the domain, written like the shopping domain. Ingredients and steps are plain text lines; `src/shared/ingredients.ts` (`parseIngredientLine`, `normaliseName`, `formatAmount`) reads them on display, and `src/shared/shoppingLines.ts` scales, rounds and merges them (`buildLines`). `POST /api/hh/plan/add-to-list` reuses `writeEntry` from `src/shopping/items.ts` and is at-least-once: the client makes the mutation id and the shopping line ids once per review. A shopping line's optional `forRecipes` is create-only and is added in every place `toShoppingItem` copies fields. Client: `app/lib/{recipes,recipeOverlay,plan,planOverlay,recipeLookup}.ts` (never decide a recipe is gone from absence alone: `lookupState`), meal mutations are the `mealMutationKeys` set in `app/lib/mutations.ts`. Cooking ticks, recipe drafts and the review state are device-local and keyed by user id (`app/lib/deviceKeys.ts`), cleared at sign-out with the rest.
- **Money** (`src/money/`, routes in `src/api/money.ts`, pure rules in `src/shared/ledger.ts`): one `MONEY#` entry per expense, loan or payment, in whole pence, storing only the other person's share. The total, loan progress and "settled" are worked out from the entries each time (`computeTotal`, `loanProgress`, `settledIds`), never stored; only agreed, live entries count. `applyEntry.ts` is the pure write rule, `entries.ts` the domain (a create or edit is `PUT /api/hh/money/{id}`), `changes.ts` the change requests on an agreed entry (one at a time, not the task proposals). Writes need exactly two members. A new entry waits for the other person to agree. Money fields change together under `version`; description and date are last-writer-wins per field. Logs hold ids, enums and pence, never a description or name (`log.ts`). Client: `app/lib/{money,moneyKeys,moneyOverlay,moneyText,moneyForm}.ts`, screens in `app/components/money/` and `app/routes/money.*`; money mutations are the `moneyMutationKeys` set in `app/lib/mutations.ts`. Wording avoids owe, debt, unpaid and behind (`BANNED_PHASE_3`). `yarn store-cli money-total <householdId>` prints a household's total and loan progress and writes nothing.
- **Calendar** (`src/calendar/`, routes in `src/api/calendar.ts`, pure rules in `src/shared/{calendar,calendarValidation,timeline,zoned}.ts`): typed events and blocks (`EVENT#`), per-person reminders (`reminders.ts`, a five-minute job, `CALREM`), and read-only feeds from a link. **Every read goes through `projectFor` (`project.ts`)**: a private event reaches the other person only as `BusyView`, and a busy-only feed only as "Busy"; sentinel tests pin this for every route, push and log. A feed link is a bearer secret: it is in a request body once, encrypted with AES-256-GCM into `CALSECRET#` (`secret.ts`, key from SSM or `CALENDAR_KEY` or `<dataDir>/calendar.key`, kept out of backups), and is never in a path, log, error, response or the app's saved cache. `fetcher.ts` only reaches the hosts in `allowedHosts.ts` (plus `CALENDAR_EXTRA_HOSTS` in the container), checks and pins the address (`addressRules.ts`), and caps time and size. `parseIcs.ts` reads a file in a worker thread with its own repeat expansion (`expandRule.ts`); `feeds.ts`, `snapshots.ts` and `refresh.ts` store month chunks and refresh them hourly from `runCalendarRefresh`. Client: `app/lib/{calendar,calendarKeys,calendarOverlay,calendarForm,calendarText,imported,useOnline}.ts`; event writes are the `calendarMutationKeys` set, but **feed actions are online only and never queued** (`app/hooks/useFeedActions.ts`), so a link is never saved on the device. `useImported(day)` reads and saves a 42-day window. The day's items come from `buildTimeline` (events, imported items, tasks due, the dinner), worked out on the device. Wording avoids failed, error, alert and warning (`BANNED_PHASE_4`). `yarn store-cli calendar-feeds <householdId>` prints feed state and writes nothing.
- **Projects** (`src/projects/`, routes in `src/api/projects.ts`, pure rules in `src/shared/projectRules.ts` and `projectValidation.ts`): a project (`PROJECT#<id>`), its steps (`PSTEP#<projectId>#<stepId>`) and materials (`PMAT#<projectId>#<lineId>`), all under `HH#<hid>`; each prefix ends in `#` and `moveOptions` lists all three. Steps are not tasks. Per-field newest-write-wins (`applyProject.ts`, `applyStep.ts`, `applyMaterial.ts`, the answer lists `stale` fields), a tombstone final for edits, and **a refused or missing record is a 200 with an outcome** (`gone`; only a project id that never existed is a 404), because a 4xx is final in the retry rules. **A hold** (`takenBy`, `takenAt`) is decided only in `holds.ts`: first to reach the server, conditional on what was read (`ifMissing`, `ifEquals`), with outcomes `taken`, `already_yours`, `held_by_other`, `done`, `gone`, `released`, `not_held`; Done is conditioned on the holder it read, and a holder who is not a current member reads as none (`holderOf`). Order is a `position` string worked out on the phone (`positionBetween`; no room means the move is refused, nothing is re-spaced). Delete tombstones the project, then gives the children its 30-day expiry in batches (`children.ts`); restore removes it first. Materials copy to the shopping list with the material's id as the item id, skipping any item that exists (`addToList.ts`), labelled through `forRecipes`. A planned day is an all-day timeline item (`buildTimeline`, type `project`); costs are two whole-pence figures that never touch the ledger. Logs hold ids, enums and counts (`log.ts`). Client: `app/lib/{projects,projectKeys,projectOverlay,projectNotices,projectLookup,projectForm,projectText}.ts`, `app/hooks/useProjectActions.tsx`, screens in `app/components/projects/` and `app/routes/plan.projects.*`; the nine-plus-three mutations are `projectMutationKeys`. A replaced edit or a refused take saves a device-local notice (the person's own words) from the registered `onSuccess`. The list route's `?counts=0` is the light read that Today and the calendar use. Wording avoids over budget, behind schedule, stuck, conflict, claim and assign (`BANNED_PHASE_5`).
- **Security events** (`src/security/events.ts`): `emitSecurityEvent` logs and publishes to SNS (`ALERT_TOPIC_ARN`); ids and event types only, never emails or names.
- **Auth0 tenant:** `docs/AUTH0.md`; the first-login Action is `infra/auth0/first-login.js`.
- **Static Lambda** (`src/static/`): serves the SPA and falls back to `index.html`.
- **Container** (`container/`): Node server plus Caddy, same handlers, SQLite store, hourly maintenance loop.
- **Frontend** (`app/`): React 19, React Router (SPA, `ssr: false`), Mantine 8, Tailwind. File routes in `app/routes/`. `~/*` maps to `app/*`. `DefaultLayout` wraps each page in `AuthProvider` and is the household gate: a signed-in person with no household goes to `/welcome` (or `/join` if an invite is waiting); `/join` is the only public page. Household data hooks are in `app/lib/household.ts`. Tasks: `useTasks()` (`app/lib/queries.ts`) polls the list and lays pending writes over it (`app/lib/overlay.ts`, pure); **every household mutation is registered once in `app/lib/mutations.ts` and used by key only** (`useHouseholdMutation`), so step 5 can persist and replay them; `app/hooks/useTaskActions.tsx` is the one place the screens run them. View rules (groups, next thing) are pure: `app/lib/tasks.ts`.
- **Offline** (`app/lib/persistedCache.ts`, `householdRuntime.tsx`, `retryRules.ts`, `app/sw.ts`): the query cache and every pending household write are saved to IndexedDB per person (`hearthwise-cache-<userId>`, with `hearthwise-user` in `localStorage` saying whose to open at launch). `HouseholdProvider` makes one client per stored person, **registers the mutations before anything is restored**, and RegisterMutations plugs the request function in later. Writes are `networkMode: 'online'` and retried by `shouldRetry` (network, timeout and lapsed sign-in for ever; 5xx three times). A restored write is resumed with `mutation.continue()` once the person it belongs to is signed in (`useResumeOnReconnect`). **Sign-out must seal the persister first** (`signOutCleanup`), or a save in flight brings the cache back; every write is bound to its owner and dropped if someone else is signed in. The worker precaches the app, never `/api/*`, never calls `skipWaiting`. `yarn test:e2e` runs the offline spike in `e2e/offline/` (Chromium; set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` to use one already installed).
- **Notifications** (`src/push/`, routes in `src/api/push.ts`): nothing is sent unless a person asked for it. `notifyOther` (called by the write routes through `src/api/notify.ts`) sends the *other* member a push only when the request had `notify: true`, the write was fresh (not a retry), and `clientAt` is under 30 minutes old; it is awaited for at most 2 seconds and never throws. During the recipient's quiet hours it writes a `HELD#` item instead, which the hourly `runSchedule` (`scheduler.ts`, shared by the push Lambda and the container's maintenance tick) releases once. The scheduler also sends each person's own digest and due nudges, claiming `lastDigestSent`/`lastNudgeSent` with a conditional update *before* sending. `PushSender` is an interface (web-push in production, a fake in tests). **A subscription's address must be a known push service** (`src/shared/pushEndpoint.ts`), checked when it is saved and again at every send. Keys: `loadVapid` (`vapid.ts`): SSM on AWS, environment or `<dataDir>/vapid.json` in the container; `/config.json` carries only the public key. The client's "Let them know" is one tick per page (`app/lib/letThemKnow.ts`), and the device check is `app/lib/push.ts`.
- **Infrastructure** (`infra/`): OpenTofu. `infra/initialSetup/` creates the deploy role and its permissions boundary and is run by hand once.

## Conventions

- Every `fetch` goes through `withTimeout()` (`app/lib/api.ts`): ten seconds, then it fails and can be retried.
- Wording is neutral and low-shame. No "overdue", "missed" or "streak"; an item past its date reads "Due". The palette has no red (`docs/brand.md`).
- Display preferences are per device and saved under `hearthwise.preferences`. Anything the household shares is saved on the server.
- Copy from the sibling app only from the pinned commit named in the design, and never change the sibling.
- Conventional commits, imperative, under 72 characters. Write the failing test first.

## Shared AWS account

The same AWS account, state bucket and GitHub OIDC provider as the sibling app are in use. So:

- Every resource name starts with `hearthwise` (`app_name`). The table is `hearthwise-data`; the SSM path is `/hearthwise/*`; state is under `hearthwise/` in the bucket.
- The deploy role is trusted from `main` only, cannot change itself, and can only create roles under the `hearthwise-lambda-boundary` permissions boundary. A pull request never gets AWS credentials.
- The deploy job fails if the plan would delete the data table or the custom domain (`scripts/check-plan.mjs`); `ALLOW_DESTRUCTIVE_DEPLOY=true` (a repository variable) overrides it for one deliberate deploy. `APP_DOMAIN` must be a repository variable, not a secret.
- `src/infra/__tests__/infraGuards.test.ts` pins these rules. A change to them is a security decision: record it in `docs/DECISIONS.md`.

## Security

Follow `SECURITY.md`. Never commit secrets, `*.tfvars` (only `*.tfvars.example`), `.env`, state, or Lambda zips. The repository is public: do not upload plan files or other build artefacts that can hold secrets.
